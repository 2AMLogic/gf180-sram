# views

Generated abstract (`LEF`) and timing (`Liberty`) views of the 256 x 32
array, driven by [klayout-tools](https://github.com/2AMLogic/klayout-tools)
(`klt`), per `CLAUDE.md`. This directory feeds `spec/sram.md`'s
"Deliverables: GDS, LEF abstract, Liberty timing" row -- the LEF abstract is
the first of the two generated views to land (issue #120); Liberty timing
(`spec/sram.md` deliverable 3) is the next seed, consuming this LEF's pin
list plus `sim/access-time/`.

## Status (2026-09-10): a real, generated LEF abstract of the array core

What is committed here is a **`klt`-generated LEF abstract of the storage-
array core** (`layout/sram_256x32/sram_256x32_array.gds`) -- not a hand-typed
placeholder, and not the foundry's own `gf180mcu_fd_ip_sram` LEF. It is the
first artifact in this directory (`views/README.md` previously read "Empty
until the first work lands here").

| | |
|---|---|
| Socket descriptor | `sram_256x32_array.socket.json` -- 322 pins (`WL0..WL255`, `BL0..BL31`, `BLB0..BLB31`, `VDD`, `VSS`), generated by `gen_socket.py` from the array generator's own drawn geometry |
| `klt socket-check` | **`status: pass`** -- outline check pass, all 322 declared pins matched (`reports/sram_256x32_array.socket-check.json`) |
| LEF abstract | `sram_256x32_array.lef` -- `MACRO sram_256x32_array`, `CLASS BLOCK`, `SIZE 143.1500 BY 1382.4000` (matches the GDS bbox exactly), 322 `PIN` blocks, 32,896 `OBS` shapes across Metal1/Metal2 |
| `klt lef-abstract` | Run unmodified under the released `klayout-tools==0.8.0` (`uvx`, never the host `klt`); the committed LEF/JSON are its output (the one `tech_lef` host-path field is `~`-redacted, see "Reproducibility and hygiene"). Issue #182 retired the runtime-patch wrapper that earlier releases needed for klayout-tools#1613 |
| Pin geometry | **322 drawn, 0 synthesized, 0 none -- `unroutable_pins[]` is empty, `warnings[]` is empty** (was 322 synthesized under klt 0.4.0 -- klayout-tools#1614 fixed; see "Pin geometry" below) |

Everything above is reproduced end-to-end by `./views/verify.sh`. What is
*not* claimed is in "What this does and does not prove".

## Scope: the storage-array core, not the 1RW macro interface

Like `layout/` and `design/` (see their own README "Scope" sections), this
abstract is of the bitcell-array **core** -- its 322 raw per-row/per-column
ports (`WL0..WL255`, `BL0..BL31`, `BLB0..BLB31`, `VDD`, `VSS`), because no
periphery (address decode, column mux, sense amps, write drivers) is drawn.
It is **not** an abstract of `spec/sram.md`'s 1RW macro pin list (`A`,
`CEN`, `CLK`, `D`, `Q`, `GWEN`, `WEN`) -- that macro-level interface does not
exist in this repo's layout yet, and neither does its LEF.

## Reproducing and re-checking

```bash
./views/verify.sh
```

It regenerates the socket descriptor (fails if it differs from the
committed bytes), runs `klt socket-check`, then runs `klt lef-abstract`
(both under the released `klayout-tools==0.8.0` via `uvx`; fails if the
regenerated `.lef` differs from the committed bytes). Individually:

```bash
# 1. socket descriptor (byte-for-byte deterministic -- git diff stays empty)
uv run --with klayout python3 views/gen_socket.py

# 2. validate it against the committed array GDS
uvx --from klayout-tools==0.8.0 klt socket-check \
    layout/sram_256x32/sram_256x32_array.gds \
    --socket views/sram_256x32_array.socket.json --format json

# 3. LEF abstract (the JSON response goes to stdout; the committed report
#    has the host's home directory rewritten to `~`, see "Reproducibility
#    and hygiene")
uvx --from klayout-tools==0.8.0 klt lef-abstract \
    layout/sram_256x32/sram_256x32_array.gds \
    --socket views/sram_256x32_array.socket.json \
    --macro-name sram_256x32_array \
    --cell-library gf180mcu_fd_sc_mcu9t5v0 \
    --class BLOCK --pdk gf180mcuD --format json \
    -o views/sram_256x32_array.lef \
  | sed "s#$HOME#~#g" > views/reports/sram_256x32_array.lef-abstract.json
```

## Pin geometry: every pin comes back `drawn`

`klt lef-abstract`'s response reports, per pin, a `geometry_source` --
`"drawn"` (real metal found at the declared position), `"synthesized"` (a
placeholder box), or `"none"` (no `PORT` at all, echoed in
`unroutable_pins[]`). Under the released `klayout-tools==0.8.0` **all 322
pins are `"drawn"`**, `unroutable_pins[]` is empty and `warnings[]` is empty.
History, since the answer changed twice:

* **Issue #120 (klt 0.4.0): 66 `synthesized`, 256 `none`.** The 256
  `WL<row>` pins were labelled on Poly2, which is not a `TYPE ROUTING` layer
  in gf180mcu's tech LEF, so there was no metal to find. A **design gap**.
* **Issue #121: 322 `synthesized`, 0 `none`.** `layout/sram_256x32/
  generate.py` reserves a 0.43 um strip at the array's left edge (where a row
  decoder would sit) and draws, per row, a Poly2 landing pad, a
  Poly2-to-Metal1 contact and a Metal1 pad flush with the macro boundary,
  then labels `WL<row>` on the Metal1 pad. Every pin still came back
  `synthesized`, because `klt lef-abstract` reused the socket's `layer`
  field (the label datatype, `Metal1_Label` (34, 10) / `Metal3_Label`
  (42, 10), which is what `klt socket-check` needs) to search for drawn
  polygons and so never looked at the drawing datatype. A **tool gap**,
  filed as klayout-tools#1614.
* **Issue #182 (klt 0.6.0): 322 `drawn`.** klayout-tools#1614 is closed and
  released; no change to the socket descriptor or the layout was needed.

What moved in the committed LEF between the synthesized and drawn
generations (`diff` of the `PIN` blocks): each `PORT` is now the real
conductor the label sits on instead of a small box around the label point.
For example `WL0` `RECT 0.0700 0.8950 0.3000 1.1250` -> `RECT 0.0000 0.8000
0.3700 1.2200` (exactly the Metal1 landing pad), `BL0` `RECT 0.6650 2.5850
0.8950 2.8150` -> `RECT 0.6300 0.0000 0.9300 5.4000` (the full bitline strap
across the bottom cell), `VDD`/`VSS` placeholders at the middle of the strap
-> the full-width Metal3 strap (e.g. `VDD` `RECT 0.4300 1377.8800 143.1500
1378.2600`). `OBS` follows: the Metal3 `OBS` shapes (2) are gone because
the supply straps are now entirely `PORT`, and Metal1 `OBS` drops from 33,088
to 32,832, exactly 256 fewer (the wordline landing-pad remainders:
each whole pad is now its pin's `PORT`, so nothing is left over for `OBS`). `SIZE` is unchanged.

Not claimed: that this LEF is *routable*. The `PORT` geometry is real drawn
metal, but `klt place-and-route` has not been run against it, and the array
core still has no periphery.

## Comparison against the foundry's own abstract

`spec/sram.md` "Corner set" already takes a comparison-not-copy stance for
Liberty; the same applies here. Read directly from the PDK's shipped
`libs.ref/gf180mcu_fd_ip_sram/lef/gf180mcu_fd_ip_sram__sram256x8m8wm1.lef`
(`~/.volare/gf180mcuD`) against this repo's own generated abstract:

| | Foundry `sram256x8m8wm1` | This repo's `sram_256x32_array` (core) |
|---|---|---|
| Scope | Full 1RW macro (`A[7:0]`, `CEN`, `CLK`, `D[7:0]`, `GWEN`, `Q[7:0]`, `WEN[7:0]`, `VDD`, `VSS` -- 37 pins) with periphery | Storage-array core only (`WL0..WL255`, `BL0..BL31`, `BLB0..BLB31`, `VDD`, `VSS` -- 322 pins), no periphery -- **not the same interface**, see "Scope" above |
| `CLASS` | `BLOCK` | `BLOCK` (same) |
| `SIZE` | 431.860 BY 340.880 um (0.1472 mm²) | 143.1500 BY 1382.4000 um (0.1979 mm²) -- exactly the GDS bbox (`layout/README.md`); 142.72 um of tiled cells plus the 0.43 um wordline landing-pad strip issue #121 added |
| `SYMMETRY` | `X Y R90` | **none declared.** The foundry macro's rows/columns are built to be mirror-safe by construction; this array's cells are tiled by plain translation only (`layout/README.md` "Area" #1: "No mirroring"), and mirrored placement of this abstract has never been checked, so this repo does not claim a symmetry it has not verified -- consistent with "no claim without a testbench" |
| Pin `USE`/`DIRECTION` | Standard LEF vocabulary: `INPUT`/`OUTPUT`/`INOUT`, `SIGNAL`/`POWER`/`GROUND` | Same vocabulary, this repo's own name-based heuristic (issue #120 Scope item 1): `WL*` `INPUT`/`SIGNAL`, `BL*`/`BLB*` `INOUT`/`SIGNAL`, `VDD` `INOUT`/`POWER`, `VSS` `INOUT`/`GROUND` |
| Pin `geometry_source` | 100% real drawn geometry (a hand/tool-authored macro LEF, not `klt`-generated) | 100% (322/322) drawn, 0% synthesized, 0% none (klt 0.6.0) -- see "Pin geometry" above |
| `OBS` layers | `Nwell`, `Metal1`, `Metal2`, `Metal3` | `Metal1`, `Metal2` (`Metal3` is entirely `PORT`; `Poly2` and `Nwell` excluded -- neither is `TYPE ROUTING` in the resolved tech LEF, so `klt lef-abstract` never represents them, matching its own documented scope: "irrelevant to a digital router working only in metal") |
| `OBS` shape count / form | A handful of large `RECT`s per layer (a coarse, macro-interior guard-box abstraction) | 32,896 shapes (32,832 Metal1 + 64 Metal2), a mix of `RECT` and `POLYGON` -- every individually-merged shape reported exactly, no coarsening. This is a real, honest difference in abstraction philosophy, not a defect in either: the foundry's own LEF trades precision for a small file (26 KB); `klt lef-abstract` has no coarsening option today, so this repo's abstract is exact but large (`sram_256x32_array.lef` is ~5 MB) |
| `FOREIGN`/`ORIGIN` | `FOREIGN gf180mcu_fd_ip_sram__sram256x8m8wm1 ; ORIGIN 0.000 0.000 ;` | `FOREIGN sram_256x32_array 0 0 ; ORIGIN 0 0 ;` (same convention, `klt`'s own default formatting) |

Macro-level area comparison is not meaningful here for the same reason
`layout/README.md` "Area" already gives for the bitcell/array: the foundry
macro is periphery-dominated and this array has none.

## Reproducibility and hygiene

- `klt` 0.8.0 (`klayout-tools==0.6.0`, PyPI, run via `uvx --from
  klayout-tools==0.8.0 klt`; the same pin `signoff/regenerate.sh` uses -- never
  the `klt` on the host)
- `klayout` pip package 0.30.12 (resolved by the `uvx` environment)
- PDK: `gf180mcuD`, tech LEF resolved via `--cell-library
  gf180mcu_fd_sc_mcu9t5v0` (the 9-track standard-cell library -- chosen
  arbitrarily; no periphery exists yet to require one library's cell heights
  over the other's, and both libraries' tech LEFs declare the same
  Metal1-Metal3 `TYPE ROUTING`/`WIDTH` values, so the choice affects neither
  the emitted geometry nor the OBS layer set)
- **PDK search-root drift, disclosed rather than pinned away.** The committed
  report's `provenance.pdk` now reads `search root: ~/.ciel`, `open_pdks
  f6eeac7dad085ffcc829ccfd721f7b4ce39edcf7` -- not the
  `c6d73a35f524070e85faff4a6a9eef49553ebc2b` under `~/.volare` that
  `layout/README.md` and `spec/pdk-variant-decision.md` pin, and that issue
  #120's report recorded. The host's PDK install moved from `volare` to its
  successor `ciel` between the two runs, and `klt` resolves whichever search
  root it finds. This changes nothing in the abstract, and that is checked,
  not assumed: the only difference between the two revisions' resolved tech
  LEFs is `ANTENNAGATEPLUSDIFF 2` -> `15` on four layers (an antenna
  parameter `klt lef-abstract` never reads), and regenerating with an
  explicit `--pdk-root ~/.volare` (the pinned `c6d73a35` tree) produces a
  **byte-identical** `sram_256x32_array.lef`. `views/verify.sh` deliberately
  does not pin a `--pdk-root`, so it keeps reproducing whatever this host
  actually has.
- No absolute host paths in any committed artifact (the #109 rule):
  `views/reports/sram_256x32_array.socket-check.json` has no PDK-derived
  field at all (`klt socket-check` never resolves one); `views/reports/
  sram_256x32_array.lef-abstract.json`'s `provenance` block already reports
  no raw path (`klayout_tools._provenance.build_provenance`: `pdk.source`
  is the literal string `"search root: ~/.ciel"`, `deck`/`input` are
  content hashes) -- the one field that leaks a resolved absolute path,
  the top-level `tech_lef` field, is rewritten to its `~`-relative form by
  the `sed "s#$HOME#~#g"` in the command above (`klt` itself prints the
  absolute path) (`~/.ciel/gf180mcuD/...`), the same symbolic
  convention `layout/README.md`'s own "Tool / PDK versions" section already
  uses.

## What this does and does not prove

**Proves** (all reproducible via `./views/verify.sh`):

* A real socket descriptor exists for the array's full 322-port interface,
  generated (not hand-typed) from the array generator's own drawn label
  geometry, and validated clean by `klt socket-check` against the committed
  GDS -- outline and all 322 pins.
* A real LEF abstract exists: `MACRO sram_256x32_array`, `SIZE` matching
  the GDS bbox exactly, one `PIN` per declared port, `OBS` covering every
  routing-layer shape not claimed by a pin.
* Every declared port has routing-layer metal on its net: `unroutable_pins[]`
  is empty and no pin reports `geometry_source: "none"`. The 256 wordlines
  reach Metal1 through a real Poly2-to-Metal1 contact per row, and that
  geometry carries its own DRC/LVS evidence (`layout/README.md`: `klt drc`
  clean on the curated *and* the PDK's own 547-rule native deck, `klt lvs`
  `status: match`, 322/322 pins).
* Two real gaps in the current tool/design surface, found by pointing `klt`
  at this design for the first time (exactly `CLAUDE.md`'s stated purpose
  for this repo) and reported honestly: a crash bug (klayout-tools#1613,
  worked around by a runtime-patch wrapper until fixed) and a pin-layer gap
  (klayout-tools#1614, disclosed as 322 `synthesized` pins until fixed).
  Both are closed upstream and released in klt 0.6.0; issue #182 removed the
  wrapper and regenerated the LEF, and **all 322 pins now carry real, drawn
  `PORT` geometry**.

**Does not prove**:

* **A routable macro.** The `PORT` geometry is real drawn metal now, but
  `klt place-and-route` has not been run against this LEF, and there is no
  periphery. Whether the abstract passes its LEF-vs-netlist wiring
  cross-check is untested -- see "Pin geometry" above.
* **The 1RW macro interface.** This is the storage-array core's raw
  per-row/per-column ports, not `spec/sram.md`'s `A`/`CEN`/`CLK`/`D`/`Q`/
  `GWEN`/`WEN` pin list -- see "Scope" above.
* **Liberty timing.** `spec/sram.md` deliverable 3, not started (the next
  seed after this one).
