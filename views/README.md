# views

Generated abstract (`LEF`) and timing (`Liberty`) views of the 256 x 32
array, driven by [klayout-tools](https://github.com/2AMLogic/klayout-tools)
(`klt`), per `CLAUDE.md`. This directory feeds `spec/sram.md`'s
"Deliverables: GDS, LEF abstract, Liberty timing" row -- the LEF abstract is
the first of the two generated views to land (issue #120); Liberty timing
(`spec/sram.md` deliverable 3) is the next seed, consuming this LEF's pin
list plus `sim/access-time/`.

## Status (2026-09-09): a real, generated LEF abstract of the array core

What is committed here is a **`klt`-generated LEF abstract of the storage-
array core** (`layout/sram_256x32/sram_256x32_array.gds`) -- not a hand-typed
placeholder, and not the foundry's own `gf180mcu_fd_ip_sram` LEF. It is the
first artifact in this directory (`views/README.md` previously read "Empty
until the first work lands here").

| | |
|---|---|
| Socket descriptor | `sram_256x32_array.socket.json` -- 322 pins (`WL0..WL255`, `BL0..BL31`, `BLB0..BLB31`, `VDD`, `VSS`), generated by `gen_socket.py` from the array generator's own drawn geometry |
| `klt socket-check` | **`status: pass`** -- outline check pass, all 322 declared pins matched (`reports/sram_256x32_array.socket-check.json`) |
| LEF abstract | `sram_256x32_array.lef` -- `MACRO sram_256x32_array`, `CLASS BLOCK`, `SIZE 142.7200 BY 1382.4000` (matches the GDS bbox exactly), 322 `PIN` blocks, 32,898 `OBS` shapes across Metal1/Metal2/Metal3 |
| `klt lef-abstract` | Blocked by a real crash bug in the installed tool (`klayout-tools#1613`) on this design's non-rectangular OBS geometry; the committed LEF/JSON were produced by `run_lef_abstract.py`, a one-line, fully-disclosed workaround for that exact bug -- see "Reproducibility and hygiene" and "How the LEF was actually produced" below |
| Pin geometry | **0 drawn, 66 synthesized (BL/BLB/VDD/VSS), 256 none (WL, `unroutable_pins[]`)** -- see "Pin geometry" below for why, layer by layer |

Everything above is reproduced end-to-end by `./views/verify.sh`. What is
*not* claimed is in "What this does and does not prove".

## Scope: the storage-array core, not the 1RW macro interface

Like `layout/` and `design/` (see their own README "Scope" sections), this
abstract is of the bitcell-array **core** -- its 322 raw per-row/per-column
ports (`WL0..WL255`, `BL0..BL31`, `BLB0..BLB31`, `VDD`, `VSS`), because no
periphery (address decode, column mux, sense amps, write drivers) is drawn.
It is **not** an abstract of `spec/sram.md`'s 1RW macro pin list (`A`,
`CEN`, `CLK`, `D`, `Q`, `GWEN`, `WEN`) -- that macro-level interface does not
exist in this repo's layout yet, and neither does its LEF.

## Reproducing and re-checking

```bash
./views/verify.sh
```

It regenerates the socket descriptor (fails if it differs from the
committed bytes), runs `klt socket-check`, then runs `klt lef-abstract`'s
underlying logic via the workaround script (fails if the regenerated `.lef`
differs from the committed bytes). Individually:

```bash
# 1. socket descriptor (byte-for-byte deterministic -- git diff stays empty)
uv run --with klayout python3 views/gen_socket.py

# 2. validate it against the committed array GDS
klt socket-check layout/sram_256x32/sram_256x32_array.gds \
    --socket views/sram_256x32_array.socket.json --format json

# 3. LEF abstract -- the documented command line (currently crashes the
#    unmodified installed tool on this design, klayout-tools#1613):
klt lef-abstract layout/sram_256x32/sram_256x32_array.gds \
    --socket views/sram_256x32_array.socket.json \
    --macro-name sram_256x32_array \
    --cell-library gf180mcu_fd_sc_mcu9t5v0 \
    --class BLOCK --pdk gf180mcuD --format json \
    -o views/sram_256x32_array.lef
# ...until klayout-tools#1613 lands and is installed, run the equivalent
# workaround instead (same library function, one line patched -- see its
# own module docstring for exactly what and why):
uv run --with klayout-tools python3 views/run_lef_abstract.py \
    layout/sram_256x32/sram_256x32_array.gds \
    --socket views/sram_256x32_array.socket.json \
    --macro-name sram_256x32_array \
    --cell-library gf180mcu_fd_sc_mcu9t5v0 \
    --class BLOCK --pdk gf180mcuD \
    -o views/sram_256x32_array.lef \
    --report views/reports/sram_256x32_array.lef-abstract.json
```

## Pin geometry: why every pin comes back `synthesized` or `none`, never `drawn`

`klt lef-abstract`'s response reports, per pin, a `geometry_source` --
`"drawn"` (real metal found at the declared position), `"synthesized"` (a
placeholder box), or `"none"` (no `PORT` at all, echoed in
`unroutable_pins[]`). Issue #120's own Scope anticipated one break (the
wordline case below) coming back `"none"`; what actually happened is
**every** pin came back `"synthesized"` or `"none"` -- **zero** `"drawn"`
pins, including the bitline and supply pins that unquestionably do have
real drawn metal at their declared positions. Both are real, reported
honestly rather than adjusted to match the anticipated outcome:

**256 `WL<row>` pins -- `geometry_source: "none"`, the anticipated break.**
Each wordline is labelled directly on Poly2
(`layout/bitcell/generate.py`'s `L_POLY2_LBL`), and Poly2 is not a `TYPE
ROUTING` layer in gf180mcu's tech LEF -- `klt lef-abstract` only ever emits
`PIN`/`OBS` geometry on routing-type layers (see its own docstring). No
metal lands on a wordline anywhere in this array's current layout, so there
is nothing for the tool to find *or* to synthesize a fallback box from (a
synthesized box still needs a resolved routing-layer `WIDTH` to size
itself). **Filed as a design gap, not a tool gap**:
[gf180-sram#121](https://github.com/2AMLogic/gf180-sram/issues/121) -- add
Metal1 landing pads for the 256 wordlines, its own PR (it moves the array's
DRC/LVS evidence, out of scope here per issue #120's "Out of scope").

**66 `BL<col>`/`BLB<col>`/`VDD`/`VSS` pins -- `geometry_source:
"synthesized"`, an unanticipated finding.** These genuinely do have real
drawn Metal1 (bitlines) or Metal3 (supply straps) at their declared
positions -- `klt drc`/`klt lvs` (`layout/README.md`) already confirm the
array's connectivity is real. The reason `klt lef-abstract` still reports
`"synthesized"` for all of them: `klt socket-check`'s own pin check requires
each declared pin's `layer` field to be the layer carrying its **text
label** ("every declared pin has a text label, on its declared layer" --
`klayout_tools.socket_check`'s own docstring), and this array's generators
label every port on a dedicated `_LBL` datatype (`Metal1_Label` (34, 10),
`Metal3_Label` (42, 10)) separate from the drawn conductor's own datatype
(`Metal1`/`Metal3` at datatype 0) -- exactly the convention gf180mcu's own
`libs.tech/klayout/tech/gf180mcu.map` encodes (`Metal1 NET,SPNET,PIN,VIA 34
0` / `Metal1 PIN 34 10`). `klt lef-abstract`'s own geometry search reuses
that *same* declared `layer` field to look for drawn polygons -- so it only
ever looks at the label datatype (text, no polygons there) and never at the
drawing datatype where the real metal actually is. There is currently no way
to declare "match the label on layer X, but look for geometry on layer Y" in
one socket descriptor. **Filed as a generic tool gap**:
[2AMLogic/klayout-tools#1614](https://github.com/2AMLogic/klayout-tools/issues/1614).
One practical consequence worth naming: the real bitline/strap metal these
pins sit on is not lost -- it still appears in this LEF's `OBS` section
(unioned independently of pin declarations) -- but a downstream P&R tool
reading this LEF would see that metal only as a routing *obstruction*, with
each pin's own `PORT` a small, disconnected placeholder box nearby, not
merged into it.

## How the LEF was actually produced (klayout-tools#1613)

The unmodified, installed `klt lef-abstract` CLI does not merely disclose a
result here -- it **crashes** with an unhandled `AttributeError` before it
can report anything, on this design's real OBS geometry (confirmed: it also
crashes on the small 4x3 tile used to develop this PR, and on the full
array). Root cause: `klayout_tools.lef_abstract._polygon_to_um_shape` calls
`simple.each_point_hull()` on a `kdb.SimplePolygon` (returned by
`polygon.to_simple_polygon()`), but `each_point_hull()` exists only on
`kdb.Polygon`, not `SimplePolygon` -- confirmed directly against the
installed `klayout` 0.30.12 package. This fires for **any** design whose
obstruction region is non-rectangular after merging, which this array's
Metal1 certainly is (8,192 instanced copies of the bitcell's L-shaped
cross-couple straps). Filed, with a minimal generic (non-SRAM-specific)
reproduction and a one-line suggested fix:
[2AMLogic/klayout-tools#1613](https://github.com/2AMLogic/klayout-tools/issues/1613).

`views/run_lef_abstract.py` is the same library function (`klayout_tools.
lef_abstract.run_lef_abstract`) the CLI itself calls, with only that one
broken method corrected in-process (`each_point_hull` -> `each_point` --
the point list is otherwise identical; no geometry, pin classification, or
OBS union/subtraction logic is touched). This mirrors an existing precedent
in this same repo for a `klt` gap on this exact array
(`layout/README.md` "Known tool gaps" #4: bypassing `klt drc --engine
klayout`'s gf180mcu-native-deck gap by invoking `klayout -b -r` directly,
while filing the gap upstream) -- work around a confirmed, minimal tool bug
to get real, honest evidence rather than let a filed bug block the
deliverable entirely. Every number in the committed `.lef`/JSON (`SIZE`,
every `PIN`/`PORT`, every `OBS` shape, `geometry_source`, `unroutable_pins[]`)
is the unmodified library's own computation -- nothing here is
hand-adjusted or fabricated. Once klayout-tools#1613 is fixed and released,
drop `run_lef_abstract.py` and switch `views/verify.sh` back to invoking
`klt lef-abstract` directly (the equivalent command line is in
"Reproducing and re-checking" above).

## Comparison against the foundry's own abstract

`spec/sram.md` "Corner set" already takes a comparison-not-copy stance for
Liberty; the same applies here. Read directly from the PDK's shipped
`libs.ref/gf180mcu_fd_ip_sram/lef/gf180mcu_fd_ip_sram__sram256x8m8wm1.lef`
(`~/.volare/gf180mcuD`) against this repo's own generated abstract:

| | Foundry `sram256x8m8wm1` | This repo's `sram_256x32_array` (core) |
|---|---|---|
| Scope | Full 1RW macro (`A[7:0]`, `CEN`, `CLK`, `D[7:0]`, `GWEN`, `Q[7:0]`, `WEN[7:0]`, `VDD`, `VSS` -- 37 pins) with periphery | Storage-array core only (`WL0..WL255`, `BL0..BL31`, `BLB0..BLB31`, `VDD`, `VSS` -- 322 pins), no periphery -- **not the same interface**, see "Scope" above |
| `CLASS` | `BLOCK` | `BLOCK` (same) |
| `SIZE` | 431.860 BY 340.880 um (0.1472 mm²) | 142.7200 BY 1382.4000 um (0.1973 mm²) -- exactly the GDS bbox (`layout/README.md`) |
| `SYMMETRY` | `X Y R90` | **none declared.** The foundry macro's rows/columns are built to be mirror-safe by construction; this array's cells are tiled by plain translation only (`layout/README.md` "Area" #1: "No mirroring"), and mirrored placement of this abstract has never been checked, so this repo does not claim a symmetry it has not verified -- consistent with "no claim without a testbench" |
| Pin `USE`/`DIRECTION` | Standard LEF vocabulary: `INPUT`/`OUTPUT`/`INOUT`, `SIGNAL`/`POWER`/`GROUND` | Same vocabulary, this repo's own name-based heuristic (issue #120 Scope item 1): `WL*` `INPUT`/`SIGNAL`, `BL*`/`BLB*` `INOUT`/`SIGNAL`, `VDD` `INOUT`/`POWER`, `VSS` `INOUT`/`GROUND` |
| Pin `geometry_source` | 100% real drawn geometry (a hand/tool-authored macro LEF, not `klt`-generated) | 0% drawn, 20.5% (66/322) synthesized, 79.5% (256/322) none -- see "Pin geometry" above |
| `OBS` layers | `Nwell`, `Metal1`, `Metal2`, `Metal3` | `Metal1`, `Metal2`, `Metal3` (`Poly2` and `Nwell` excluded -- neither is `TYPE ROUTING` in the resolved tech LEF, so `klt lef-abstract` never represents them, matching its own documented scope: "irrelevant to a digital router working only in metal") |
| `OBS` shape count / form | A handful of large `RECT`s per layer (a coarse, macro-interior guard-box abstraction) | 32,898 shapes (32,832 Metal1 + 64 Metal2 + 2 Metal3), a mix of `RECT` and `POLYGON` -- every individually-merged shape reported exactly, no coarsening. This is a real, honest difference in abstraction philosophy, not a defect in either: the foundry's own LEF trades precision for a small file (26 KB); `klt lef-abstract` has no coarsening option today, so this repo's abstract is exact but large (`sram_256x32_array.lef` is ~5 MB) |
| `FOREIGN`/`ORIGIN` | `FOREIGN gf180mcu_fd_ip_sram__sram256x8m8wm1 ; ORIGIN 0.000 0.000 ;` | `FOREIGN sram_256x32_array 0 0 ; ORIGIN 0 0 ;` (same convention, `klt`'s own default formatting) |

Macro-level area comparison is not meaningful here for the same reason
`layout/README.md` "Area" already gives for the bitcell/array: the foundry
macro is periphery-dominated and this array has none.

## Reproducibility and hygiene

- `klt` 0.4.0 (`klayout-tools` 0.4.0, both the `uv tool install
  git+https://github.com/2AMLogic/klayout-tools` build and the PyPI
  `klayout-tools` package -- same version, same bug)
- `klayout` pip package 0.30.12 (`uv run --with klayout-tools`), 0.30.10 via
  the pipx-installed `klt` binary -- the crash reproduces on both
- PDK: `gf180mcuD`, `open_pdks` commit
  `c6d73a35f524070e85faff4a6a9eef49553ebc2b` (same pin as `layout/README.md`
  and `spec/pdk-variant-decision.md`), tech LEF resolved via
  `--cell-library gf180mcu_fd_sc_mcu9t5v0` (the 9-track standard-cell
  library -- chosen arbitrarily; no periphery exists yet to require one
  library's cell heights over the other's, and both libraries' tech LEFs
  declare the same Metal1-Metal3 `TYPE ROUTING`/`WIDTH` values, so the
  choice affects neither the emitted geometry nor the OBS layer set)
- No absolute host paths in any committed artifact (the #109 rule):
  `views/reports/sram_256x32_array.socket-check.json` has no PDK-derived
  field at all (`klt socket-check` never resolves one); `views/reports/
  sram_256x32_array.lef-abstract.json`'s `provenance` block already reports
  no raw path (`klayout_tools._provenance.build_provenance`: `pdk.source`
  is the literal string `"search root: ~/.volare"`, `deck`/`input` are
  content hashes) -- the one field that did leak a resolved absolute path,
  the top-level `tech_lef` field, is redacted by `run_lef_abstract.py` to
  its `~`-relative form (`~/.volare/gf180mcuD/...`), the same symbolic
  convention `layout/README.md`'s own "Tool / PDK versions" section already
  uses.

## What this does and does not prove

**Proves** (all reproducible via `./views/verify.sh`):

* A real socket descriptor exists for the array's full 322-port interface,
  generated (not hand-typed) from the array generator's own drawn label
  geometry, and validated clean by `klt socket-check` against the committed
  GDS -- outline and all 322 pins.
* A real LEF abstract exists: `MACRO sram_256x32_array`, `SIZE` matching
  the GDS bbox exactly, one `PIN` per declared port, `OBS` covering every
  routing-layer shape not claimed by a pin.
* Two real gaps in the current tool/design surface, found by pointing `klt`
  at this design for the first time (exactly `CLAUDE.md`'s stated purpose
  for this repo) and reported honestly rather than worked around silently:
  a crash bug (klayout-tools#1613, worked around here with full disclosure)
  and a pin-layer design limitation (klayout-tools#1614, not worked around
  -- every metal-backed pin's `PORT` is a placeholder box) that together
  mean **no pin in this LEF has real, drawn `PORT` geometry today**.

**Does not prove**:

* **A routable macro.** Every pin's `PORT` is either absent (`WL*`, 256 of
  322) or a small synthesized placeholder disconnected from the real metal
  it sits on (`BL*`/`BLB*`/`VDD`/`VSS`, the remaining 66) -- see "Pin
  geometry" above. `klt place-and-route` cross-checks a hard macro's LEF
  `PIN` blocks against the netlist's actual wiring before invoking OpenROAD;
  this LEF would not pass that check today.
* **The 1RW macro interface.** This is the storage-array core's raw
  per-row/per-column ports, not `spec/sram.md`'s `A`/`CEN`/`CLK`/`D`/`Q`/
  `GWEN`/`WEN` pin list -- see "Scope" above.
* **Liberty timing.** `spec/sram.md` deliverable 3, not started (the next
  seed after this one).
