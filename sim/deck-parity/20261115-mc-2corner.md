# Deck-mode parity receipt 20261115 -- first live Monte Carlo, two corners, three MC families

- **What this is**: the **first live run of the Monte Carlo deck-mode path**
  (`deck_adapter.py mc-build` / `mc-reduce`, PR #238's offline adapter) for the
  staged `klt sim` deck-mode migration (#230). Two corners of the committed MC
  matrix (`tt_25c_3.30v`, `ff_125c_2.97v`), the three families that have
  committed MC records (`read-snm`, `hold-snm`, `write-margin`), at the
  committed campaign's own sample counts (`--n 200 --n-control 4 --n-nc 100
  --seed 20260817`, each family's own `--nc-mismatch-scale`/`--nc-vdd`), as one
  `klt sim --batch-set` of three members: **3,040 deck units** (1,216 + 1,216 +
  608). Graded by `mc-reduce`, compared by `parity_compare.py mc` against the
  committed per-sample arrays.
- **What this is not**: a new characterization claim. No record under
  `sim/*/mc/records`, `sim/*/mc/samples`, `sim/*/mc/yield-reports` or
  `sim/*/mc/raw-logs` was minted, edited or superseded, and no `klt yield`
  report was generated. It is evidence about the **generator**: does deck-mode
  transport reproduce the committed campaign's per-sample values, its
  determinism-control anchors, and its errored draws?
- **Authorization**: the 2026-11-14 operator ruling on #230 (bounded parity runs
  on the corner/MC matrix; "The Curator may also schedule the follow-up corners
  that parity needs"), and the 2026-11-15 curated increment scheduling exactly
  this two-corner run. The hand-rolled launchers
  (`sim/lib/run_corner_sweep.sh`, the `run_mc_campaign.py` pool) stay in place;
  cutover is not part of this run.
- **Result**: **parity holds for all three families at both corners.** Every
  one of the 200 mismatch samples per (family, corner) reproduces its committed
  per-sample value: `write-margin` **exactly** (400/400, zero delta on every
  sample), `read-snm`/`hold-snm` **exactly under the pre-#213 `--pair`
  extractor** (400/400, max delta 0.0 V -- the 30 uV gate was never
  approached). Every corner's 4 determinism-control samples collapse onto one
  value equal to the committed deterministic record (exact for `write-margin`
  and `read-snm`'s recorded metric; within 3 uV for `hold-snm`'s recorded
  metric and within 1-14 uV for its lobes, same residual class as the
  deterministic grid). Every corner's
  negative-control errored count equals the committed record's (`1`/`4`,
  `0`/`0`, `6`/`2`), and every usable nc value matches in surviving order. Deck
  bytes and per-unit seeds asserted on all 3,040 returned units.

## How it was run

```bash
# three mc-build requests (a single corner is refused by build_mc_request:
# "at least two corners are required"); each family its own nc parameters
python3 sim/lib/deck_adapter.py mc-build read-snm \
  --corner tt:25:3.30 --corner ff:125:2.97 \
  --n 200 --n-control 4 --n-nc 100 --nc-mismatch-scale 20 \
  --seed 20260817 --stage-dir <scratch>/stage/read-snm \
  --request-out <scratch>/stage/read-snm/request.json
# hold-snm:     --nc-mismatch-scale 12 --nc-vdd 0.50
# write-margin: --nc-mismatch-scale 6  --nc-vdd 0.60
# (deck requests resolve relative unit paths against the request file's own
# directory, so each request lands inside its stage dir)

# one batch-set submit for all three members (never a local grid)
klt sim --batch-set <scratch>/stage/read-snm/request.json \
        <scratch>/stage/hold-snm/request.json \
        <scratch>/stage/write-margin/request.json \
  --max-in-flight 3 --wait-for-capacity 600 \
  -o <scratch>/out --report-out <scratch>/batch-set-envelope.json --format json

# caller-owned grading -- never the engine's exit status
python3 sim/lib/deck_adapter.py mc-reduce <family> <request.json> <report.json> \
  --outdir <out>/<member> --json-out <family>-reduced.json

# mechanical comparison against the committed sample-sets (re-runnable)
git show e140796^:sim/lib/snm_extract.py > <scratch>/pre213_snm_extract.py
python3 sim/lib/parity_compare.py mc <family> <family>-reduced.json \
  --request <request.json> --report <report.json> \
  --unit-dir <out>/<member> --sweep-dir <out>/<member> \
  --pre213 <scratch>/pre213_snm_extract.py --json-out <family>/parity-summary.json
```

## Assertions, all made by the comparator

`parity_compare.py mc` (`--request --report --unit-dir`) asserts per unit,
because `mc-reduce` checks seeds and coverage but performs **no deck-bytes
check at all** (measured 2026-11-15 against `origin/main` @ `05fa343`;
`reduce_mc_report` contains zero `deck_sha256` references -- a larger gap than
#347, which is the corner path's fail-open-on-absence):

- **Deck bytes**: all 3,040 returned units report a `deck_sha256` that is
  present and equal to their request's `composed_deck_sha256`. An absent field
  fails; `mc-reduce`'s silence is not evidence. (#347 hardened the corner
  path's `reduce_report` to fail closed on absence while this receipt was in
  flight; `reduce_mc_report` remains check-free on the post-#347 tree, so
  this comparator assertion is still the only deck-bytes check on the MC
  path.)
- **Seed identity**: all 3,040 returned unit trees carry a `corner.inc` whose
  `.options seed=` equals
  `run_mc_campaign.derive_seed(20260817, corner_id, kind[-side], index)`,
  re-derived by the comparator from the request's `base_seed` -- checked
  against the *returned* bytes, not the manifest's own copy.
- **Reducer grading**: `coverage_errors: []` on all three members; member 1
  and 2 `overall: recorded`; member 0's five infra failures are all nc units
  (graded below, never as parity).

The determinism-control anchor is the committed **deterministic** record
(`RECORD_CLAIMS` / `latest_record_for_claim()` / `parse_record()`), exactly
the anchor the MC harness itself claims (`run_mc_campaign.py`'s ctrl batch is
documented as "must equal what run_corner_sweep.sh's deterministic record
reports"). `write-margin @ tt_25c_3.30v` = 1.91003 is both the MC record's
pinned control value and the deterministic record's RESULT -- reproduced
exactly here. The `hold-snm` 3 uV / 14 uV lobe residuals are the same
compatibility-mode-attributed class the deterministic grid measured (worst 7
uV there; the gated `hold_snm_v` metric at 3 uV is 10x under the 30 uV
gate -- the 14 uV worst lobe is ~2x under it but tabulated, not gated).

The mismatch-batch result is the strongest claim in this receipt: **the same
1,200 mismatch draws** (200 per family per corner) produced the **same value
to every digit** as the pool's 2026-09-21 campaign -- 2,000 mm decks in total
(1,600 SNM half-cell decks + 400 direct), same seeds, same unmodified
testbench bytes, same corner includes, executed by a different scheduler on
different hardware.

## What is re-derivable from committed bytes

Per the bounded-bytes rule (this receipt introduces it for MC; the raw-sweep
rule of the deterministic receipts does **not** scale -- one committed SNM
sweep is ~22 KB, so committing all of them would have been ~52 MB for these
two corners alone):

- **Re-derivable**: `write-margin`'s exact-match claim (raw `RESULT:` lines
  committed per corner as `result-lines.txt`, from every unit's stdout, unit
  labelled); the deck-bytes claim (`report.json` + each request's
  `composed_deck_sha256`); the seed-identity claim for the committed
  representative `corner.inc.*` files; the nc errored-count comparison
  (`reduced.json` nc tallies vs the committed sample-set); and the full ctrl
  anchor (all 16 ctrl sweeps per SNM family committed under `sweeps/`; the
  direct family's 8 ctrl units per corner are re-derivable from the `ctrl`
  RESULT lines in its committed `result-lines.txt`).
- **Spot-auditable, not fully re-derivable**: the SNM per-sample mismatch
  claim (first 5 mm sample indices per (family, corner) committed with both
  sides' sweeps; the remaining 195 samples per corner are summarised in
  `parity-summary.json`'s per-sample deltas). Re-running the full comparison
  requires the collected out tree, which is not committed.
- **Not re-derivable**: the seed-identity claim for the ~3,034 units whose
  `corner.inc` is not committed (representatives only per (corner, kind,
  side); every unit's seed is in the committed `request.json` manifest, the
  comparator's per-unit check result is in `parity-summary.json`).

## Limits

- **Two corners of nine.** The committed MC campaign covers 9 corners per
  family; this receipt covers `tt_25c_3.30v` (the nominal anchor) and
  `ff_125c_2.97v` (the tightest-margin corner: lowest committed read-SNM mean
  and Cpk of the nine). The remaining **7 corners are unmeasured** by any
  live MC deck-mode run; blocker 2's MC half is met for these two corners
  only.
- **Three of five families.** `read-access` / `write-access` have no
  committed MC record, so there is nothing to compare them against; running
  them would be a new characterization claim, which no ruling authorizes.
- **Compatibility mode (#338)**: every unit's stdout carries the worker's
  `Note: No compatibility mode selected!` while the 2026-08 record logs carry
  `Note: Compatibility modes selected: hs a` -- deck mode does not transport
  the executing host's `.spiceinit`. Despite that, every mismatch value
  reproduced exactly and every residual stayed within 14 uV; the caveat
  stands until #338/PR #346 pins the mode.
- **The worker publishes no PDK stamp** (`PDK_ROOT=/opt/pdk`, `variant:
  null`), so `pdk_stamp_comparison` / `models_lib_comparison` remain
  `not_comparable`; the per-sample agreement above is the evidence the worker
  resolved equivalent models.
- The MC campaign itself was run under PDK pin `c6d73a35...` (see the
  sample-set provenance); the deterministic grid's re-qualification under
  `f6eeac7` is #272. This receipt's exact per-sample agreement is evidence
  the *transport* is faithful, not that the PDK pin question is settled.
