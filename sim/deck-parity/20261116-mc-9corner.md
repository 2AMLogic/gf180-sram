# Deck-mode parity receipt 20261116 -- Monte Carlo, the full committed 9-corner matrix, three MC families

- **What this is**: the **complete Monte Carlo half of blocker 2** for the
  staged `klt sim` deck-mode migration (#230). The committed MC matrix is
  9 corners per family; `sim/deck-parity/20261115-mc-2corner.md` covered two
  of them. This receipt covers **all nine** -- `read-snm`, `hold-snm`,
  `write-margin` x every corner of the committed sample-sets, at the
  committed campaign's own sample counts (`--n 200 --n-control 4 --n-nc 100
  --seed 20260817`, each family's own `--nc-mismatch-scale`/`--nc-vdd`) --
  **13,680 deck units** (5,472 + 5,472 + 2,736) across 21 fleet jobs, graded
  by `mc-reduce` and compared by `parity_compare.py mc` against the committed
  per-sample arrays.
- **What this is not**: a new characterization claim. No record under
  `sim/*/mc/records`, `sim/*/mc/samples`, `sim/*/mc/yield-reports` or
  `sim/*/mc/raw-logs` was minted, edited or superseded, and no `klt yield`
  report was generated. It is evidence about the **generator**: does
  deck-mode transport reproduce the committed campaign's per-sample values,
  its determinism-control anchors, and its errored draws?
- **Authorization**: the 2026-11-14 operator ruling on #230 (bounded parity
  runs on the corner/MC matrix; "The Curator may also schedule the follow-up
  corners that parity needs") and the 2026-11-15 curated increment that
  scheduled the 2-corner run as stage 1 of exactly this matrix, deferring
  "the remaining 7 MC corners" to the next increment. This receipt is that
  increment, extended to all 9 corners because the first submit already
  staged the full matrix (see "How it was run"): the 7 new corners are new
  evidence, the 2 already-receipted corners re-run under the pinned
  `.spiceinit` (#338/#346) as an internal control. The hand-rolled launchers
  stay in place; cutover is not part of this run.
- **Result**: **the transport parity claim holds everywhere it can be
  tested.** Every one of the **5,400 mismatch samples** (200 per family per
  corner) reproduces its committed value within the 30 uV gate -- `write-margin`
  **exactly** (1,800/1,800, max delta 0.0 V), `read-snm` worst 2 uV,
  `hold-snm` worst 6 uV, 0 `OPEN`. Every determinism-control anchor
  (4 per corner x 9 corners x 3 families = 108 samples) collapses onto the
  committed **deterministic** record **exactly** (delta 0.0 V on every
  recorded metric, every corner, every family). The committed records'
  negative-control **errored counts** match the fleet's on **all 27
  (family, corner) cells** -- the fleet reproduced not only the values but
  *which draws* fail. Deck bytes (present-and-equal `composed_deck_sha256`)
  and per-unit seed identity (`derive_seed`) are asserted on **all 13,680
  returned units** with zero errors.
- **Finding (new, fully attributed)**: the SNM **negative-control surviving
  values** -- the deliberately known-bad draws -- diverge from the committed
  arrays on a minority of draws (`read-snm`: 2 of 1,800; `hold-snm`: 65 of
  1,800; `write-margin`: 0), and the cause is **not the transport**: a
  controlled local A/B (same host, same ngspice 47, same deck bytes, same
  seeds, only the `.spiceinit` differing) reproduces the committed value
  **exactly** with an empty `.spiceinit` and the fleet-class value with the
  #338/#346 pinned one. In other words: **the committed MC campaign ran
  unpinned**, while the committed *deterministic* campaign ran with
  compatibility modes (`hs a`) -- and #346's pin, which makes deck mode match
  the deterministic records exactly (see the ctrl column: 0.0 V everywhere,
  vs 1-14 uV residuals in the unpinned 2026-11-15 run), moves the SNM
  negative-control numerics off the MC records' environment. Which
  environment future campaigns standardize on is an evidence-policy question
  this receipt records but does not settle (see "Limits").

## How it was run

### Provenance first: the staged requests are byte-identical to main's

This run is the **completed first submit plus one bounded completion submit**,
not a from-scratch campaign. The 2026-11-16 03:13Z submit crashed mid-upload
after its shards had already run and been collected (below), leaving its
scratch tree intact at `/tmp/g230`. Before reusing any of it, `mc-build` was
re-run on the issue worktree (then at `origin/main` @ `24aab92`) with the
identical arguments, and the three staged `request.json` files compared
byte-for-byte:

```
read-snm/request.json      IDENTICAL (cmp)
hold-snm/request.json      IDENTICAL
write-margin/request.json  IDENTICAL
```

The request carries the source-testbench sha256, the composed-deck sha256,
every unit's `derive_seed` value, and the `.spiceinit` input hash -- so byte
identity pins decks, seeds and environment inputs to exactly what main
stages today. Nothing was hand-edited anywhere in the tree.

### Phase 1: the first submit (03:13Z), 16 of 21 shards ran and were collected

The full 9-corner campaign was submitted as three family requests with
`--max-units-per-job 684` (21 shards). Uploads are serial per file
(`2AMLogic/klayout-tools#5880`); while shards 6-7 (`read-snm`), 6-7
(`hold-snm`) and 4 (`write-margin`) were still uploading, the submitting
process was killed by its session teardown, which also reaped the process's
temp directory -- the surviving client died with
`FileNotFoundError: .../klt-batch-*/request.json` mid-submit. The 16 shards
already uploaded had launched, run and been collected by 03:16Z (their
`status.json` shows state `done`/`failed` with the job's own verdict exit
code; `failed` = exit 4, the aggregate reflection of errored negative-control
units, not a transport failure). Their local unit trees and per-shard reports
survive; the five never-submitted shards' job ids were printed but never
registered (status 404 to this day) and cost nothing.

### Provenance check, then phase 2: the missing shards (05:07Z)

The five missing shard id-sets were read from the phase-1 shard map, filtered
into per-family `request-missing.json` files **in the same stage directories**
(the deck entries are self-contained relative paths), re-checked against the
same byte-identical staging, and submitted as three blocking `klt sim` runs
(`--backend batch --max-units-per-job 684 --wait-for-capacity 600`). They
split into 2 + 2 + 1 shards, uploaded, ran and were collected by 05:39Z
(2 x 684 `read-snm`, 2 x 684 `hold-snm`, 1 x 547 `write-margin` -- 3,283
units of new spend; the other 10,397 units are phase 1's already-executed
work being reused, not re-run).

### Grading and comparison

Per family, the two phases were stitched back into the single deck report a
blocking run would have written (`report.json`'s `environment.remote`
records every job of both phases; units are copied **verbatim** from the
per-shard reports klt itself wrote, in manifest order -- the stitcher asserts
exact id-order coverage against the request before writing). Then:

```bash
python3 sim/lib/deck_adapter.py mc-reduce <family> <request.json> <report.json> \
  --outdir <collected-unit-tree-root> --json-out <family>-reduced.json
git show e140796^:sim/lib/snm_extract.py > <scratch>/pre213_snm_extract.py   # byte-checked vs e140796^
python3 sim/lib/parity_compare.py mc <family> <family>-reduced.json \
  --request <request.json> --report <report.json> \
  --unit-dir <collected-unit-tree-root> --sweep-dir <collected-unit-tree-root> \
  --pre213 <scratch>/pre213_snm_extract.py --json-out <family>/parity-summary.json
```

The envelope/status fields are process-level only and are never read as a
measurement: grading is `mc-reduce`'s (exit 0 is never a PASS), comparison is
`parity_compare.py mc`'s.

Headline per family (full mechanical tables committed as
`<family>/parity-compare.md`, machine summaries as

(`sim/<family>/mc/samples/20260921-*.json`) predate the #213 extractor
change, so both SNM families are compared through the pre-#213 extractor's
`--pair` mode applied to the fleet's own returned per-sample sweep pairs,
gated at the same **30 uV** the deterministic grid used. The determinism
control is the committed **deterministic** record
(`RECORD_CLAIMS` / `latest_record_for_claim()` / `parse_record()`).

**Mismatch batch (the measurement) -- 5,400/5,400 compared, 0 `OPEN`, gate

### The pin-attribution experiment (committed under `pin-attribution/`)

Three diverging draws were re-run locally as a controlled A/B: identical
deck bytes, `corner.inc` and seeds, same host, same `ngspice 47`, same
pre-#213 `--pair` extractor -- the only variable is the staged `.spiceinit`
(#338/#346's pinned environment) vs an empty one:

| Draw | Committed | Local **unpinned** | Local pinned | Fleet pinned |
|---|---|---|---|---|
| `hold-snm` @ `tt_25c_3.30v` nc 68 | 0.166776 | **0.166776 (exact)** | 0.095418 | 0.095418 (exact) |
| `read-snm` @ `ff_-40c_2.97v` nc 2 | 0.723965 | **0.723965 (exact)** | 0.672731 | 0.121380 |
| `read-snm` @ `tt_25c_3.30v` nc 22 | 1.022704 | **1.022704 (exact)** | 1.001150 | 0.106307 |

- **Unpinned reproduces the committed value exactly, every time.** The
  committed MC campaign ran in an unpinned-like environment.
- Local pinned == fleet pinned exactly for `hold-snm` nc 68 (0.095418): the
  local probe is a faithful fleet replica. For the two `read-snm` draws,
  two pinned executions of the *same deck* land in different metastable
  wells (0.67 vs 0.12; 1.00 vs 0.11) -- these 20x-sigma draws sit on the
  bistability knife-edge, which is exactly why they are negative controls
  and why the committed campaign excluded a matching set of them outright.
- Conclusion: **the nc divergence is the #338/#346 environment change
  interacting with known-bad draws -- not deck-transport error.** The pin
  was merged to make deck mode reproduce the *deterministic* records'
  environment, and it does (ctrl exact); the *MC* records were simply taken
  under the other environment.

## Limits

- **Negative controls are not measurements.** The nc batch is the
  deliberately known-bad variant (12-20x the PDK mismatch sigma, one family
  at reduced VDD). Its divergence under the pinned environment is attributed
  above, but the recorded `parity` verdicts for `read-snm` (7/9) and
  `hold-snm` (0/9) corners stand as the comparator wrote them: under
  today's pinned generator, SNM nc arrays are not value-identical to the
  September records. Anyone quoting nc arrays as evidence should read the
  pin-attribution section first.
- **Two environments, one evidence base -- needs a policy call.** The
  deterministic records (2026-08) carry `Compatibility modes selected: hs a`
  and are reproduced exactly by the pinned generator; the MC records
  (2026-09-21) are reproduced exactly by the *unpinned* generator. Both are
  committed append-only evidence; neither is wrong, but future campaigns
  cannot match both at once. Which environment future evidence
  standardizes on is a spec/evidence-policy decision (spec/ decision
  record) that this receipt does not make.
- **The committed MC campaign ran under PDK pin `c6d73a35...`** (sample-set
  provenance); this run executed under the current `f6eeac7` pin. The
  exact mm agreement (and #272's deterministic re-qualification) is the
  evidence the pin change did not move the cell.
- **The worker publishes no PDK stamp** (`PDK_ROOT=/opt/pdk`, `variant:
  null`), so `pdk_stamp_comparison` / `models_lib_comparison` remain
  `not_comparable`; the per-sample agreement is the evidence the worker
  resolved equivalent models.
- **`--max-units-per-job` splitting is a workaround**, not a preference:
  a single 5,472-unit deck job uploads one `aws s3 cp` subprocess per file
  and would have taken hours (`2AMLogic/klayout-tools#5880`). The split
  path made the upload concurrent; its scratch-dir fragility (the phase-1
  crash) is recorded in the same issue's thread.
- **Single-point probes stay local**; nothing here changes the cold-start
  section of `sim/README.md` (still not to be run on dispatch workers).

## Verdict for the staged migration

Blocker 2 (*measurement parity*) is **met for the entire committed MC
matrix**: every measured value (mismatch batch) and every determinism
anchor reproduces within/at the gate at all 9 corners x 3 families, errored
draw sets match everywhere, and deck bytes + seeds are asserted on all
13,680 units. Blocker 3 (*cutover*: retiring `run_corner_sweep.sh` and the
MC pool, switching defaults, rewriting the cold-start section) is the
remaining increment -- plus the environment-standardization decision above,
which it should be staged behind. Per the operator ruling, this PR is
`Part of #230`, not a closing reference.
