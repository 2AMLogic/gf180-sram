# Deck-mode parity receipt 20261114 -- `tt_25c_3.30v`, all five families

- **What this is**: the bounded measurement-parity run the staged `klt sim`
  deck-mode migration (#230) needs before cutover -- blocker 2 of
  `sim/README.md` "Staged migration to `klt sim` deck mode". One corner
  (`tt_25c_3.30v`) per characterization family, executed in `klt sim` **deck
  mode on the 2am EDA batch fleet**, graded by `sim/lib/deck_adapter.py
  reduce`, and compared against the committed record value for the same
  corner.
- **What this is not**: a new characterization claim. No record under
  `sim/*/records/` was minted, edited or superseded, and nothing here changes a
  recorded measurement. It is evidence about the **generator** (does deck-mode
  transport reproduce the launcher's numbers?), not about the cell.
- **Authorization**: operator ruling of 2026-11-14 on #230 ("Run the bounded
  parity run on the batch fleet: one corner per family through `klt sim` deck
  mode, results and job ids on this issue"), which lifted the hold the
  2026-10-19 ruling placed on live validation. The hand-rolled launchers stay
  in place; cutover is not part of this run.
- **Corner**: `tt_25c_3.30v` (process `tt`, 25 C, VDD 3.30 V) -- the nominal
  point of the ratified 27-corner matrix, present in every family's committed
  record.

## How it was run

```bash
# one bounded request per family (--corner is #230's bounded-run selection)
for fam in read-snm hold-snm write-margin read-access write-access; do
  python3 sim/lib/deck_adapter.py build "$fam" --corner tt:25:3.30 \
    --stage-dir /tmp/deck-parity-230/stage/"$fam" \
    --request-out /tmp/deck-parity-230/stage/"$fam"/"$fam".json
done

# one batch job per family, submitted as a set (never a local grid)
klt sim --batch-set /tmp/deck-parity-230/stage/*/*.json \
  --max-in-flight 5 --wait-for-capacity 600 \
  -o /tmp/deck-parity-230/batch-out \
  --report-out /tmp/deck-parity-230/batch-set-envelope.json --format json

# caller-owned grading, coverage pinned to the request's own corner list
for fam in read-snm hold-snm write-margin read-access write-access; do
  python3 sim/lib/deck_adapter.py reduce "$fam" \
    /tmp/deck-parity-230/batch-out/"$fam"/report.json \
    --request /tmp/deck-parity-230/stage/"$fam"/"$fam".json
done
```

Every reduce exited `0` with `overall: recorded`. `recorded` is the reducer's
own grading of `RESULT:`/`RESULT-ERROR:` lines (and `snm_extract.py` for the
DC-sweep families), not the engine's exit status: deck mode reports process
success only, and exit 0 is never read as a measurement pass.

### The two SNM families: the #213 extractor fix, isolated

`read_snm_v` / `hold_snm_v` are not emitted by the testbench; they are computed
from the testbench's swept data file by `sim/lib/snm_extract.py`. That
extractor changed in `e140796` (issue #213: the SNM side is the gap along
`y = x` divided by sqrt(2), not the vertical curve gap, which over-reads).
`sim/README.md` "Earlier SNM values over-read (issue #213)" already records
that the committed SNM values use the old, over-reading measure and were
deliberately not edited. So the committed SNM numbers cannot be compared to a
current-extractor value at face value, and the table above is not a generator
discrepancy.

Applying the **pre-#213** extractor to *this run's* fleet-produced sweep data
separates the two effects (`snm-pre213-crosscheck.log` in the run directory):

| Family | Metric | Committed record | Pre-#213 extractor on fleet data | Delta |
|---|---|---|---|---|
| `read-snm` | `read_snm_v` | `0.381267` | `0.381267` | **exact** |
| `read-snm` | `read_snm_lobe_low_v` | `0.857685` | `0.857683` | -2 uV (2.3 ppm) |
| `hold-snm` | `hold_snm_v` | `1.110807` | `1.110810` | +3 uV (2.7 ppm) |
| `hold-snm` | `hold_snm_lobe_low_v` | `2.035532` | `2.035546` | +14 uV (6.9 ppm) |

With the reducer held fixed, the fleet's deck-mode run reproduces the committed
SNM numbers to within 3 uV on the recorded metric (<= 7 ppm on the lobe
intermediates), on an identical 661-row sweep. That is numerical noise between
two ngspice builds, not a different measurement: **generator parity holds for
all five families.**

### Why the residual microvolts (a real environmental difference)

The committed 2026-08 corner logs carry `Note: Compatibility modes selected: hs
a`; this run's worker stdout carries `Note: No compatibility mode selected!`.
ngspice's compatibility mode comes from the *executing host's* `.spiceinit`,
which deck mode does not transport (and the current dispatch host does not set
either -- `~/.spiceinit` here sets only `wnflag`/`num_threads`). The two SNM
families, whose metric is a geometric construction over 661 swept points, show
this as a few microvolts; the three families with their own `.meas`-style
`RESULT:` lines show it as nothing at all. Pinning the mode explicitly in the
request (`klt sim`'s `options.ngspice_init`) would remove the dependence on
whatever the executing host happens to configure; that is tracked in #338 and
is **not** part of this receipt.

## Limits

- **One corner, one sample per family.** `tt_25c_3.30v` only. This receipt says
  nothing about the other 26 ratified corners, and nothing about the Monte Carlo
  adapter (`mc-build`/`mc-reduce`), which still has no live run of any kind.
- **The worker's PDK revision is not verifiable from the report.** The worker
  reports `PDK_ROOT=/opt/pdk` with `variant: null` and no PDK stamp, so
  `pdk_stamp_comparison` is `not_comparable` (`reason:
  worker_stamp_unavailable`) and `models_lib_comparison` is `not_comparable`
  (`reason: runner_hash_unavailable`). The measurement agreement above is the
  only evidence that the worker resolved equivalent models; the pinned-revision
  check `sim/lib/pdk_env.sh` performs locally has no counterpart on the fleet.
- **Spot instances, a different ngspice build.** `ngspice 47` built
  2026-11-13 on the worker, versus whatever the 2026-08 record host ran; the
  residual microvolts above are the measured size of that difference at this
  corner, not a bound for every corner.
- **Not a cutover.** `sim/lib/run_corner_sweep.sh` and the
  `run_mc_campaign.py` process pool are untouched and remain the documented
  procedure. Retiring them is blocker 3 and needs its own decision.
